# Sacred Communication Protocol

Sacred Gold работает в 32-битном процессе, а загрузчик модов использует
64-битную JVM. Поэтому Java-моды запускаются в отдельном `java.exe`, а
JavaScript-агент внедряется в игру через Frida. Агент и хост обмениваются
сообщениями Frida. Между хостом и JVM кадры идут через стандартные потоки
дочернего процесса, по одной строке UTF-8 на кадр. Хост пишет в stdin JVM и
читает её stdout. Агент не обращается к JVM напрямую. Формат кадров описан в
[docs/PROTOCOL.md](docs/PROTOCOL.md).

`protocol.exe` ждёт запуска игры, внедряет агента из репозитория
[coderpack](https://github.com/ancaria-dev/coderpack), запускает
`dev.ancaria.coderpack.zygote.Main` с `api.jar` и `zygote.jar` в classpath и
передаёт кадры между агентом и JVM. Хуки существуют только в памяти процесса
игры.

## Как запустить

Обычно `protocol.exe` запускает лаунчер. Его можно запустить вручную из
установленной папки:

```
<Sacred Gold>\launcher\protocol.exe
```

Если игра запущена с правами администратора, хост тоже нужно запускать
с правами администратора. Иначе Frida не сможет подключиться, хотя хост будет
видеть процесс и продолжит ждать. Без аргументов пути определяются относительно
исполняемого файла.

## Кадры протокола

Пример сессии:

```
EVT 2 hero.captured class=9 className=Daemon level=142 hp=27127 maxHp=27127
ASK 3 health.damage entity=player damage=553 current=19849 next=19296 max=26999
END 3 set.next=19849
```

`EVT` сообщает о завершившемся событии и не требует ответа. `ASK` отправляется
до записи значения и останавливает поток игры на время ожидания. Ответ `END`
разрешает операцию без изменений, отменяет её или переписывает поля. В примере
`set.next=19849` сохраняет прежнее здоровье и тем самым отменяет урон до записи.

Мод может сам отправить команду:

```
CMD 1 player.gold
RES 1 ok=1 gold=104233
```

Протокол также определяет `LOG` и `BYE`. В ключах и значениях процентное
кодирование применяется только к `%`, пробелу, `=`, переводу строки и возврату
каретки. Остальные символы остаются без изменений, поэтому кадры читаются
прямо в терминале.

`ASK` блокирует поток игры, поэтому действуют три ограничения:

- **У вердикта есть дедлайн.** Сторожевой поток проверяет запросы каждые 125 мс
  и считает `ASK` просроченным, когда его возраст превышает 250 мс. Затем хост
  ставит в очередь `END ok=1` и записывает номер запроса в журнал. Обычно это
  происходит через 250–375 мс, не считая задержек планировщика и цикла отправки.
  Медленный мод теряет право вето для этого запроса. Если JVM завершается, хост
  отключает дальнейшие ожидания `ASK`, а затем завершает работу.
- **Тот, кто отвечает на `ASK`, не должен в том же потоке читать ответы.** Мод,
  который вызывает игру из обработчика события, создаёт взаимную блокировку.
  Чтение и отправка разведены по разным потокам.
- **В stdout идут только кадры.** Логи идут в stderr. Мод, печатающий через
  `System.out`, повреждает поток, и хост сообщает о строке, которую не удалось
  разобрать как вывод Coderpack. Для сообщений загрузчик предоставляет
  собственный интерфейс журналирования.

На Windows хост пытается поместить JVM в job object с
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Процесс игры в этот объект не входит. JVM
завершается вместе с хостом, только если объект создан, ограничение настроено и
процесс JVM успешно присоединён. Ошибка создания или настройки выводит
предупреждение, но не останавливает хост. Ошибка присоединения сейчас остаётся
без сообщения, поэтому гарантия завершения JVM условна.

## Поиск проблем с хуками

Флаги позволяют отключать модули и отдельные точки подключения без пересборки:

| Флаг | Что делает |
|---|---|
| `--skip gold,position` | не грузить эти модули агента |
| `--only health` | грузить только этот модуль (`core`, `bus` и `names` загружаются всегда) |
| `--no-hook goldEpilogue` | оставить модуль, но не подключать указанную точку |
| `--trace` | выводить сообщение при каждом срабатывании хука |
| `--no-ask` | оставить хуки включёнными, но отключить вердикты |

Между попытками нужно перезапускать игру. Если завершился только хост,
внедрённый агент может остаться в процессе, и новый хост попытается повторно
изменить уже подключённую инструкцию.

Имя модуля совпадает с именем файла агента без числового префикса. Аргументы
`--agent`, `--dist`, `--mods` и `--java` переопределяют пути, а `--enable`
задаёт идентификаторы загружаемых модов. Без `--java` хост сначала ищет
`java/bin/java.exe` рядом с собой, куда лаунчер распаковывает скачанный JDK.
Затем проверяется `%JAVA_HOME%\bin\java.exe`, после чего используется `java` из
`PATH`. Обычно лаунчер явно передаёт скачанную Java через `--java`. Для
настоящего запуска хоста требуется JDK 21 или новее. Неизвестный аргумент
завершает запуск с ошибкой.

## Сборка

```
cargo build --release
```

Результат находится в `target/release/protocol.exe`. Для сборки нужны Rust 1.98
с MSVC toolchain и LLVM. `frida-sys` запускает bindgen, которому требуется
libclang. В `.cargo/config.toml` для `LIBCLANG_PATH` задано
`C:\Program Files\LLVM\bin`, но уже установленная переменная окружения имеет
приоритет. Предупреждение линковщика `LNK4098` вызвано статическим CRT в
frida-core и динамическим CRT Rust. Для этой сборки оно ожидаемо.

В `vendor/frida` находится исправленная копия крейта `frida` 0.17.2. Для
сообщений, отличных от `frida:rpc`, исходная версия приводит `user_data`
обратного вызова к типу обработчика вызывающей стороны. Фактически там хранится
`CallbackHandler`, поэтому первый `send()` от агента завершал хост с
`0xC0000005`. Подробности приведены в `vendor/README.md`. Регрессионная проверка
требует `python` в `PATH`, подключается к временному процессу и ждёт сообщение
не более 5 секунд. Игра ей не нужна:

```
cargo run --example message_check
```

`cargo test --release` сейчас запускает шесть тестов кодека кадров, сборщика
агента и границы с JVM. Два теста сборщика используют собственную фикстуру из
`tests/agent` и не читают `../coderpack`. Сквозной тест запускает настоящую JVM
Coderpack без модов и проверяет, что каждый `ASK` получает кадр, который может
разобрать хост. Он выбирает лексикографически новейшие JAR-файлы `api` и
`zygote` в соседнем checkout coderpack или в локальном Maven-репозитории
(`~/.m2/repository/dev/ancaria/coderpack`). Если файлов нет, тест выводит
сообщение о пропуске и завершается успешно.

CI работает на Windows при push в `master`, для pull request и при ручном
запуске. Проверка `cargo fmt --check` не блокирует сборку. Затем CI выполняет
release-сборку и release-тесты, а `protocol.exe` загружается как артефакт
каждого запуска. После успешного push в `master` CI читает `version` из
`Cargo.toml`. Если удалённого тега `v<version>` ещё нет, шаг публикации создаёт
этот тег и релиз с файлом `target/release/protocol.exe`. Изменение версии
выпускает релиз только после успешного завершения шага публикации. Лаунчер
скачивает этот файл, когда собирается без соседнего checkout протокола.
